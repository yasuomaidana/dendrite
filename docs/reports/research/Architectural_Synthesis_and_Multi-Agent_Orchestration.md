Across its five core workspaces—dendrite-control (Go orchestration under pkg/agent and pkg/sandbox), dendrite-core-rs (Rust abstract syntax tree [AST] analysis and quality gates), dendrite-rag-rs (Rust hybrid vector and symbol retrieval), dendrite-git-rs (Rust isolated worktree lifecycle), and dendrite-mcp-hub (centralized tool gateway)—the architecture enforces 13 foundational pillars governed by strict sliding-window token caps (FEAT-002) and a local-first escalation hierarchy (OxiLLaMa :8080 $\rightarrow$ Ollama $\rightarrow$ AGY $\rightarrow$ Claude). Introducing frontier large-context models alongside self-improving agent harnesses and concurrent multi-agent protocols requires a disciplined phasing strategy that prevents runtime collisions, eliminates memory split-brain, and preserves token economics.Resolving the Hermes Agent, Gentle-AI, and Engram TrilemmaA central architectural question for the develop branch is whether adopting Hermes Agent (NousResearch/hermes-agent) creates structural conflicts with Gentle-AI (Gentleman-Programming/gentle-ai) and its persistence engine, Engram (Gentleman-Programming/engram). An examination of the underlying binaries and runtime lifecycles demonstrates that Gentle-AI and Hermes operate at different abstraction layers, yet running Hermes's default autonomous daemon loop alongside Gentle-AI introduces severe state and token-governance collisions unless specific subsystems are decoupled.Gentle-AI is not an autonomous large language model (LLM) runtime; rather, it is a deterministic Go-based ecosystem configurator created by Alan Buscaglia that equips existing host agents—explicitly supporting 17 runtimes including Claude Code, OpenCode, Antigravity (agy), and Hermes itself—with Organic-Driven and Spec-Driven Development (ODD/SDD) workflows, bounded review guardrails, and the Engram memory server. Engram compiles as a standalone, zero-dependency Go binary backed by a local SQLite and FTS5 full-text search database (~/.engram/engram.db) exposed via stdio Model Context Protocol (MCP) tools (mem_save, mem_search, mem_context, mem_session_summary, mem_get_observation, mem_merge_projects) and Git-based team synchronization (engram sync writing to .engram/). Furthermore, Engram classifies knowledge into typed bullets (FACT, DECISION, PREFERENCE, GOAL, PROCEDURE, PRINCIPLE), assigns salience scores based on importance and recency, resolves contradictions with version history, and assembles context strictly within a caller-supplied token budget. Conversely, Hermes Agent is a full Python agent runtime built by Nous Research that implements passive self-improvement via spawn_background_review in agent/background_review.py. After any conversation turn that crosses a complexity threshold—defined as more than five tool calls, an error recovery sequence, or an explicit user correction—Hermes forks a background daemon thread that replays the session snapshot and invokes skill_manage (create, edit, patch, write_file) in skill_manager_tool.py to mutate reusable Markdown files under ~/.hermes/skills/ in the agentskills.io format.Deploying Hermes out-of-the-box alongside Gentle-AI and dendrite-control triggers three critical failure modes that compromise workspace determinism. The first failure mode is memory split-brain and cron degradation. Hermes maintains an internal four-layer memory hierarchy comprising MEMORY.md (capped at 2,200 characters or approximately 800 tokens), USER.md (capped at 1,375 characters or approximately 500 tokens), FTS5 session search, and external plugins such as the SQLite Holographic Reduced Representations (HRR) vector algebra backend (memory.provider: holographic). If an agent writes architectural decisions to Hermes's MEMORY.md or its SQLite fact_store while Claude Code and Antigravity query Gentle-AI's Engram (~/.engram/engram.db) and dendrite-rag-rs, cross-agent context fractures immediately. Moreover, Hermes's internal cron scheduler hardcodes skip_memory=True (cron/scheduler.py:1686), which disables the entire memory subsystem during scheduled runs—rendering memory(), fact_store, and fact_feedback unavailable—and forces Phase 2 promotions in nexus9888/hermes-memory-skills to degrade into direct file patches on MEMORY.md while leaving interactive holographic facts uncondensed.The second failure mode involves unbounded background side-effect leakage and scope violations. In Hermes's spawn_background_review implementation, the forked review agent historically inherited the host agent's broader toolset. As documented in Hermes Issue #15204, a background skill-review fork created a collaboration skill (subagent-file-path-and-draft-safety) via skill_manage and then continued executing outside its responsibility boundary, invoking terminal tools to communicate with another agent over tmux while impersonating the active host agent. Similarly, Hermes Issue #72082 demonstrated that spawn_background_review fires at turn finalization based on tool-iteration counters (memory.nudge_interval: 10, skills.creation_nudge_interval: 15) rather than user turns, causing background threads to mutate skill trees and create undisclosed files even when the user explicitly scoped the turn as read-only or report-only. Additionally, Hermes Issue #100762 revealed that setting auxiliary.background_review.enabled: false silently dropped manual bare /refine invocations until patched in v0.21.0. Although upstream releases (v2026.4.30) restricted the background review fork to memory and skills toolsets and introduced skills.write_approval: true alongside hermes curator pin, allowing an unmonitored Python daemon to mutate .agents/skills/ bypasses Dendrite's Pillar 12 supervisory middleware.The third failure mode is auxiliary token exhaustion and curator overwrite conflicts.
